# Repository checks

Moved from the README: this repository's local Warden gates, its CI, its Nox Security workflow, and how Ghostline decides whether to trust a Nox report.

## Local gates, CI and the Security workflow

This repository's `.warden.yaml` configures Warden developer gates: Go tests and a tracked-repository Nox scan before commits, then Go tests, `go vet`, frontend tests/build, and another Nox scan before pushes. The Warden steps call Nox directly. Its `trusted_keys` list defines whose signed local validation notes the repository accepts; update that list deliberately when a maintainer signing key changes. Install Warden (for example, `go install go.klarlabs.de/warden@v0.46.1`) and Nox 1.67.0, the version used by the Security workflow, from the [official release](https://github.com/Nox-HQ/nox/releases/tag/v1.67.0), placing its `nox` binary on `PATH`. Then run `warden init --hooks=pre-commit,pre-push` in a fresh checkout to activate the hooks. Nox uses the committed `.nox/baseline.json` to identify accepted findings. Warden removes stale scan output, requires a fresh report, and runs `nox ci-gate`, matching CI policy: any code-security finding and net-new critical/high findings above the baseline block; new medium/low findings remain reported but do not block. Required-analyzer gaps also fail the gate. These hooks help contributors catch issues early. Hosted security and validation evidence should come from repository CI checks attached to a commit; Ghostline displays those checks only for the commit they ran against.

Pull requests also run GitHub Actions CI for Go tests/vetting and frontend tests/builds. Actions run with read-only repository permissions and are pinned to commit SHAs.

The `Security` GitHub Actions workflow runs the SHA-pinned Nox Marketplace action with Nox 1.67.0 on pull request revisions and pushes to `main`. For a pull request it checks out and scans the PR head commit, not GitHub's merge preview, and attributes the code-scanning upload to that commit. It uploads SARIF to code scanning, runs `nox ci-gate`, and keeps the JSON/SARIF output, with `scanned-commit.txt` naming the commit that was checked out and scanned, as a `nox-results` artifact for 7 days. The `nox-results` path is reserved for that output: the job fails if the scanned revision tracks it, and removes anything else there before scanning, so a pull request cannot plant files in the artifact, redirect its writes with a symlink, or hide files from the scan. The gate fails on a missing report, a required analyzer that did not run, any code-security finding (HARDEN, PERM, CRYPTO, MEMSAFE), net-new critical or high findings above the committed `.nox/baseline.json`, or a baseline entry that no longer matches a finding. Medium and low findings remain visible and reported without blocking the gate. Pushes to `main` also create or reopen one GitHub issue per untracked Nox fingerprint rated medium or above (or without a severity); informational and low findings stay in the report and SARIF only; baseline entries whose reason links an issue are already tracked and do not create duplicates. Each issue links the scan run and the exact scanned commit. Ghostline retrieves these artifacts by exact run and commit SHA, validates the GitHub artifact digest, and accepts Nox SARIF 2.1.0. It accepts a report only when GitHub supplies the run's PR base SHA and the workflow file there matches the scanned revision; a missing base SHA (as for fork PRs), an unreadable base workflow, or a mismatch leaves the report untrusted. It also rejects the report when the pull request changes a file that steers the scan (the workflow, `.nox.yaml`, anything under `.nox/` (including the baseline), any `.gitignore`, and the `nox-results` scan output path), when that cannot be verified, or when `.nox.yaml` moves the baseline. The artifact's `scanned-commit.txt` must name the requested revision; artifacts without it, including those from before the workflow scanned the PR head, are untrusted. The base SHA is not documented as immutable execution provenance; matching workflow content is corroborating context only. Artifacts are not attested, so treat them as run output rather than signed provenance. Ghostline shows the source run, revision, and report retention expiry with findings.

## How Ghostline matches a Nox report to a revision

Nox reports are matched through GitHub Actions workflow runs and their `nox-results` artifacts. Ghostline accepts a report only when the workflow file at the scanned revision matches the pull request base, preventing a PR-edited workflow from supplying a fabricated clean report; it shows findings, report availability, expiry, and the source run. It says explicitly when a report is missing or expired and never treats an earlier revision's checks or scan as evidence for the current head.
